## Historical Prototype Finding

Before real profile support landed, the benchmark suite had the three relevant
operations, but the byte-lane prototype was labeled too much like a real Aura0
file operation. The runtime result was useful, and byte-lane raw/lz4/zstd9 won
against external zstd L3 in that JSON, but `aura0-byte-lane-to-aura1-bytes`
timed a generated prototype payload, not a serialized Aura0 file.

## Product Target Operations

- Compact semantic Aura0 to Aura1 bytes:
  - operation: `aura0-to-aura1-bytes`
  - current profile label: `aura0-compact-semantic`
- Historical prototype byte lane to Aura1 bytes:
  - operation: `aura0-byte-lane-to-aura1-bytes`
  - current profile label: `aura0-fast-byte-lane-prototype`
- External Aura1.zst to Aura1 bytes:
  - operation: `zstd-aura1-to-aura1-bytes`
  - baseline label: `zstd`

All three fair byte-output paths use `output_sink=memory_vec`.

## Verification Separation

Production operations leave `output_bytes_equal` and `output_byte_hash` null.
Verify variants compute output equality and output byte hash. This is correct:
the production target must not include guard/hash verification unless the zstd
baseline includes equivalent work.

## Important JSON Fields

- `input_bytes`: original CLI input file size.
- `benchmark_input_bytes`: actual timed byte buffer size.
- `aura0_compressed_bytes`: compact semantic Aura0 size.
- `aura1_zstd_compressed_bytes`: external `.aura1.zst` size.
- `byte_lane_compressed_bytes`: historical prototype byte-lane payload size.
- `aura1_uncompressed_bytes`: target Aura1 byte size.

The old flaw: prototype byte-lane JSON reported `source_format=aura0` even
though the timed buffer was the generated byte-lane payload. Real file support
now routes the benchmark through production Aura0 files instead.
